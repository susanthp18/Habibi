## Diagnosis verified

Two live `python -m worker` processes (PIDs 35744, 33264) poll every 2s (`--poll` default `2.0`, worker.py:382) via `process_one` → `claim_next_job` — `WHERE status='queued' ORDER BY created_at ASC FOR UPDATE SKIP LOCKED LIMIT 1` (kb_ingest.py:151). Exactly the query the test races. Incidental corroboration: two orphaned probe rows from my aborted simulator runs came back as `status='failed'` with `minio_get_failed: ... NoSuchBucket: kb-sources` — a live worker had claimed them and tried to genuinely index the document. The theft is real and it does production work on the way past.

## Mechanism chosen: detection (prevention is not available)

Prevention would need to block foreign `FOR UPDATE SKIP LOCKED` claimers. The only table-lock mode that conflicts with their `ROW SHARE` is `EXCLUSIVE`/`ACCESS EXCLUSIVE` — which would equally block the two racing connections and destroy the race being tested. So: **window minimisation + proof-based detection.**

1. **Window minimisation** — both claimer threads now open their connection and transaction *before* the probe job is inserted, parking on a 3-party barrier that the main thread joins. Exposure drops from "two thread starts + two pool checkouts" to "one INSERT commit + one barrier release."
2. **Proof, in three signals**, only consulted when neither thread got the probe:
   - Post-race row state read with **blocking `FOR UPDATE`** (no SKIP LOCKED), sharing the cleanup transaction, under `SET LOCAL lock_timeout='10s'` — it *waits out* a thief's in-flight transaction rather than racing it. Catches the committed claim (`status='running'`, `started_at` set) or a vanished row.
   - `visible` — could an empty-handed claimer see the row as queued at all.
   - `lockable` — was the row lock free. Visible-but-unlockable is the only signal that catches a foreign claimer whose transaction later **rolls back**, which leaves no other trace.

If none of the three fires, nothing foreign is implicated and the original assertions run and fail.

## A defect the negative control caught

My first detector version was wrong and I only found it because I tested the failure direction. The two claimers' own probes take the row lock for the length of a savepoint, so one claimer could see its *partner's* momentary lock and report "a third session has it" — excusing a genuine defect as worker contention:

```
[negative control] *** SKIPPED — a real defect was excused: ... claimer 1 saw the
queued probe row but its row lock was held by a third session
```

Fixed with a `probe_gate` lock serialising the probes. The savepoint bounds how *long* the lock is held, not *when*; both guards are needed and the comment says so.
