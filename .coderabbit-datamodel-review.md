# In-depth data-model review (schema only)

You are performing the deepest possible **production data-model review** of this collections CRM. Review the **current schema as it exists today**, not just git hunks.

## Scope — stay inside this

IN:

- `backend/sql/*.sql` — authoritative base DDL (loaded in filename order)
- `backend/alembic/versions/*.py` — every schema change since the baseline
- `backend/DATA_MODEL.md` — domain map / ERD / intended invariants
- `backend/alembic/env.py` only if it changes search_path, RLS, or tenant GUC

OUT (do not review):

- Python runtime, FastAPI routes, voice/Pipecat, Habibi UI, prompts, seeds-as-demo-data, tests, Docker

If a finding is not about tables, columns, types, constraints, indexes, FKs, views, triggers, tenancy, migrations, or PII-at-rest, drop it.

## Product facts (use these; do not fight them)

- PostgreSQL 16 + pgvector. Enums are `TEXT` + `CHECK`, not PG enum types. That is intentional.
- Shared DB + `tenant_id` on top-level tables. Local Postgres is the collections CRM SoR, **not** the bank CBS/LMS.
- `work_items` is a **VIEW** over domain tables, not a base table.
- Polymorphic handlers are `(kind, user_id, bot_id)` triplets.
- Money must be `numeric`, never float. Timestamps must be `timestamptz`.
- Indian BFSI: RBI collections, DPDP, TRAI DND. Contact policy, consent, and audit must be enforceable from the schema, not only from app code.

## Required depth (walk every table)

For **each** table in `sql/` plus every table created/altered in alembic, check:

1. **Tenancy**
   - Does a tenant-owned row carry `tenant_id` (or a parent that does, with a real FK)?
   - Unique keys that should be per-tenant: is `tenant_id` in the unique/PK?
   - Cross-tenant join holes (child FK to a parent in another tenant with no composite FK).
   - RLS / `app.tenant_id` GUC: present, missing, or bypassable? Say which. Do not assume RLS exists.
   - Config tables that are global vs tenant-scoped — is that documented and enforced?

2. **Integrity**
   - Missing FK, wrong `ON DELETE` (CASCADE on money/audit/PII vs SET NULL vs RESTRICT).
   - Polymorphic handler without a CHECK that exactly one of user/bot is set for that kind.
   - Partial unique indexes and NULL: Postgres treats NULLs as distinct — flag holes (treatment_holds already calls this out; look for the same bug elsewhere).
   - Idempotency keys for inbound payments, webhooks, provider refs.
   - Append-only logs (`audit_log`, `activity_events`, `contact_events`, `authority_decisions`, `treatment_decisions`, `live_qa_decisions`) that still have `updated_at` or no revoke-insert pattern.
   - `CHECK` lists that drifted from DATA_MODEL.md statuses.

3. **Money, time, identity**
   - Amounts, APR, outstanding, EMI, budgets: `numeric(p,s)` vs INTEGER paise vs float.
   - Running balances stored vs derived — can they diverge from `ledger_entries`?
   - `now()` vs `clock_timestamp()` on append-only logs written twice in one transaction.
   - TEXT ids vs UUID; FK type mismatches.

4. **PII / DPDP / retention**
   - Phone, email, address, DOB, PAN, Aadhaar, account numbers, recordings, transcripts: stored how?
   - Redaction tables vs live operational copies that never get masked.
   - Export jobs that can dump unredacted rows.
   - Missing `tenant_id` on PII tables. Missing retention/purge columns where the doc promised them.
   - Consent/DND/frequency-cap tables that cannot actually enforce a cap (no unique day key, nullable channel, etc.).

5. **Migrations & drift**
   - `sql/` says one thing, a later alembic revision says another, and they never reconverge.
   - Baseline SQL loaded then alembic stamped — duplicate CREATE vs missing ALTER.
   - Destructive drops, column type changes without rewrite, CHECKs added that fail on existing rows.
   - Revisions that are seed-only mixed into schema (call out only if they change constraints).
   - Untracked revisions `0059`–`0085` and `sql/14`–`sql/20` are in scope.

6. **Performance that is a correctness risk**
   - Tenant list queries with no `(tenant_id, …)` index on the access path the CRM actually uses (queue, PTP due, DND, bounce).
   - Unbounded jsonb blobs as the only place a legally required field lives.

## Output bar

- Every finding must cite file + object (table/index/constraint name) and the failure mode.
- Severity: `critical` = data leak, money desync, tenant bleed, irreversible destroy. `major` = integrity/enforcement hole. `minor` = real but contained. No style nits, no “consider adding a comment”.
- Do not restate DATA_MODEL.md. Contradict it when the DDL is wrong, or contradict the DDL when the doc over-claims (e.g. “RLS” that is not in SQL).
- Walk the ERD spine: tenants → customers → accounts → ledger/EMI → interactions → promises/disputes/callbacks/docs → consent → violations/QA → redaction → work_items view.
